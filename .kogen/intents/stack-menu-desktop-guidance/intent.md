# Add conditional desktop framework guidance

Slug: stack-menu-desktop-guidance
Model: not applicable — the change adds static editorial records and deterministic derivation of them; it has no stateful behavior.
Acceptance:
- .kogen/intents/stack-menu-desktop-guidance/acceptance.feature
- features/steps/stack-menu-desktop-guidance__steps.js

This Intent gives desktop applications an honest path with no full profiles. It adds `desktop` as an accepted component and role, and a task `desktop-app` (label "Desktop application") whose starting point is an uncurated lead. The requests `{component:"desktop"}` and `{use_case:"desktop-app"}` both return 200 with `curated:false`, empty candidates, the coverage-gap nudge and the consequential question.

Schema. The task carries `curated: false` (absent means curated, as today) and a string `question`. Its `primary` is the stable ID of an uncurated alternative, `tauri-2-desktop`, whose record has `profile_id: null`, `use_cases: ["desktop-app"]`, `choose_when`, `caveat` and official `sources`. The primary ID never refers to a profile or generator. A curated task still needs a known profile primary, so a curated task with a `null` primary is rejected. An uncurated task must carry `sources`, `why`, `tradeoff` and `question`, and its primary must be a null-profile alternative that belongs to the task. The compiler (`scripts/recommendation_content.py`) accepts `desktop` in `COMPONENTS`, validates the uncurated case, excludes the lead alternative from the task's other alternatives by alternative id (not only by profile id), and in `choose.md` renders the uncurated lead with its trigger, caveat, sources and the question, keeping the primary ID in backticks as the existing task-primary Markdown representation does. `lib/recommendation-policy.js` resolves the same exclusion. `scripts/build-schema.mjs` accepts a null-profile primary only for `curated:false`.

Router (`lib/router.js`). `component` accepts `desktop`; with `goal` choose and no `use_case`, `component: desktop` infers `desktop-app`. `recommendation.primary` is `{id, title, feasible:null, conditional: false, curated: false}` where `title` is the lead alternative's label; curated tasks keep their existing primary object unchanged. `candidates` is empty (no profile has a `desktop` kind, and no web profile may match through `kind`). The existing nudge "default profile … not present in the current catalogue" (the one at `router.js:100`) must not fire for the uncurated primary as if this were a defect; instead a coverage-gap nudge says no curated Stack Menu profile covers desktop applications, the lead is a research lead, and no web, CLI or mobile profile is substituted. The task `question` is added to the route `questions`. A `goal:build` request with an unlisted `existing_stack` and `component: desktop` keeps today's research path (`existing_source.unknown_source`, the inventory question, no substitute, no candidates, preserve-selected-stack nudge).

Chooser (`public/design/interactive.js`). For an uncurated primary the card shows the lead's label as its title, an "Uncurated starting lead" eyebrow, the lead's `choose_when`, the task `why`, `tradeoff` and `question`, and sources; it has no guide button and no "matching guide is not present" text. Alternatives render as for other tasks (`choose_when`, `caveat`, sources, no guide link).

Content (`menu/recommendations.json`). Editorial content, each item with official sources that the Build re-verifies when it writes the records: lead Tauri 2 (use stable 2.x; 3.0 is alpha; web-technology UI fits, system-webview differences per OS accepted, no contrary constraint; Rust owns native commands); alternatives `electron-desktop` (consistent bundled Chromium across OSes, in-process Node.js APIs or Electron ecosystem matter more than bundle size; 8-week major cadence and only the latest three majors supported, so an upgrade obligation), `compose-multiplatform-desktop` (Kotlin/JVM team, or sharing UI and logic with Android and Kotlin Multiplatform; desktop is Stable), `gpui-desktop` (conditional, Rust teams wanting GPU-rendered non-webview UI who accept pre-1.0 breaking changes; crates.io release lags upstream and platform statements differ from upstream main; pin an exact revision and qualify every target OS) and `native-single-os-desktop` (platform-native single-OS clients such as SwiftUI/AppKit on macOS; Windows-native/.NET stays an explicit coverage gap, not a recommendation). The task `tradeoff` states this is not universal Tauri superiority, that native-rendering, accessibility or platform-integration requirements override the webview default, and that a chosen desktop stack is preserved under `goal:build`. The `question` asks one consequential thing: whether a web-technology UI and per-OS system-webview differences are acceptable, or native rendering, accessibility or platform integration is required, and which OS targets apply. The other preferences (Rust, Kotlin or JS team; single OS or cross-platform) live in the `choose_when` triggers, not in new router enums. No profile, generator record, rewrite source or version number is added to scenarios.

Documentation. `scripts/build-menu.py` "Target surfaces" gains Desktop. `content/agent-entry.md` gains a desktop bullet (uncurated lead, research path, preserve a chosen desktop stack) and `content/routing.md` lists the `desktop` component and the new task and updates its task count. `menu/inputs/research/catalogue.json` keeps "Desktop stack preparation" in `coverage_gaps`. Evidence status stays documentation-reviewed; no starter execution is claimed. The Build records a browser inspection of the new card at desktop width and 390 px through the maintained preview route, or states it could not; no new browser dependency is added. Existing scenarios under `tests/scenarios/` stay unchanged and green; `tests/scenarios/compiler_validation.py` is not edited. No sponsor content, deployment or push.
