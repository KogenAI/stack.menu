# Add offline scenario baseline command

Slug: stack-menu-scenario-baseline
Model: not applicable — the change adds a read-only offline check command and project records; it has no stateful behavior of its own.
Acceptance:
- .kogen/intents/stack-menu-scenario-baseline/acceptance.feature
- features/steps/stack-menu-scenario-baseline__steps.js

This Intent adds one offline command, `npm run check`, that encodes Stack Menu's existing preservation behavior as named scenario tests and runs them against the current, unmodified product. It does not repair product behavior: `lib/`, `functions/` and `menu/` stay byte-for-byte unchanged in this item, and `package.json` dependencies, `devDependencies`, the `build` script and `package-lock.json` stay as they are. Acceptance checks these kept constraints first, in a scenario that passes on the unchanged tree, separately from the new command's behavior.

`npm run check` is a `package.json` script that runs `npm run build` first, then `node --test` over scenario test files (new files, in a new directory of the builder's choosing, using only Node's built-in `node:test`/`node:assert`), then a Python 3.9+ stdlib-only step for compiler validation. It uses no network, browser, preview server, model call or new dependency. No assertion depends on prose wording, page/reference/candidate counts, ordering, absolute paths, a running server or source slicing of `public/design/interactive.js`. Compiler negative fixtures run on in-memory or temporary copies, never by editing `menu/`. Acceptance observes only zero versus non-zero completion of the script text and the scenario names in its output, not an exact exit value through a package-manager wrapper.

Each scenario is a top-level `node:test` test whose name starts with `scenario <n>: ` (n = 1..8 as below), so the spec reporter output names it. The eight scenarios:

1. Nine task baselines. Using `routeContext` from `lib/router.js` with `goal:"choose"` and `use_case`, the literal editorial primaries are: `content-site`→Astro (profile `astro-content`), `web-product`→Rails (`rails-hotwire-postgresql`), `live-web`→Phoenix (`elixir-phoenix-liveview`), `admin-web`→Django (`python-django`), `browser-client`→React+Vite (`typescript-react-vite-browser`), `api-service`→Go service (`go-service`), `cli`→Go CLI (`go-cli`), `automation`→Python (`python-scripts-workers`), and `cross-platform-mobile` without a platform → Expo (`expo-react-native`) with primary.conditional:true (that is, `recommendation.primary.conditional` is true), `role_options` [ios, android] (`recommendation.use_case.role_options` deep-equals `["ios","android"]`) and a pending shared-vs-platform question (non-empty `questions`). Each override also resolves: python→Django/FastAPI (admin-web → `python-django`, api-service → `python-fastapi`), php→Laravel (`laravel-livewire-postgresql`), ruby (admin)→Rails (`rails-hotwire-postgresql`), elixir→Phoenix (`elixir-phoenix-liveview`), react→Next (`typescript-next-node`), rust→Rust service/CLI (api-service → `rust-service`, cli → `rust-cli`), `ios`→SwiftUI (`swift-swiftui-ios`), `android`→Compose (`kotlin-compose-android`), `shared`→Expo (`expo-react-native`); the `ios`, `android` and `shared` overrides are the `mobile_platform` values. The four legacy aliases `python-api`, `react-fullstack`, `ios`, `android` map with their original preference; a conflicting alias preference (for example `use_case:"python-api"` with `ecosystem:"php"`) throws an error.
2. Explicit stack preserved. For every profile ID in `lib/selection-index.json` (derived at run time, not hard-coded), `goal:"build"` with `existing_stack` set to that ID and conflicting `use_case`, `ecosystem` and `component` values yields candidates == [that id], no `recommendation` key, and a leading nudge that tells the agent to preserve the selected stack.
3. Hard constraints. `use_case:"web-product"` with `static_only:true` keeps `recommendation.primary.id` as `rails-hotwire-postgresql` with `feasible:false` and a nudge that the default does not satisfy a hard constraint; it is never replaced. A `ui` preference filters candidates only with explicit component:web.
4. Migration. Identical source and target yields the installed-version question and no replacement plan. A role mismatch (for example Next.js→Go CLI: `existing_stack` the Next.js profile `typescript-next-node`, `target_stack` `go-cli`) yields clarification questions, a missing-roles nudge and keeps both resources. A source-only ID (`wordpress`) is accepted as `existing_stack` and rejected as `target_stack` with HTTP 400 through the handler. An unlisted source yields a research question, existing_source.unknown_source:true and no language matching.
5. Mobile/Expo. An existing Expo (`expo-react-native`) build with component:ios stays Expo (the only candidate) and does not introduce `swift-swiftui-ios`.
6. Handler statuses via `functions/route.js` `onRequest` with Node `Request` objects: 400 for an unknown field, a bad enum or a repeated GET field; 413 for a body over 16 KiB; 415 for the wrong content type; 405 for an unsupported method; GET query results deep-equal the corresponding `routeContext` results.
7. Compiler negative fixtures. `load_policy` in `scripts/recommendation_content.py` rejects (raises `ValueError`) an unknown primary, an alternative whose ID is outside its task, an override condition not declared in `constraints`, and an alternative without sources, each on an in-memory or temporary copy of the policy.
8. Representation agreement, built from `dist/`: `dist/recommendations.json` is equivalent to `menu/recommendations.json` (or its documented projection); every task's resolved primary ID and each applicable alternative's `choose_when` appear in `dist/choose.md`; `dist/design/{recommendation-policy,migration-fit}.js` (that is, `dist/design/recommendation-policy.js` and `dist/design/migration-fit.js`) are byte-equal to the files of the same names in `lib/`; every rewrite source and profile advertises HTML/MD/JSON files that exist under `dist/`.

The command runs on the unchanged source before any fix. Any scenario that fails on the unchanged source is classified as pre-existing, recorded with its diagnostic, and expressed as a strict named expected failure (a test that fails if it unexpectedly succeeds); expectations are never edited to match current output without that classification. Expo template lint/TypeScript failures, the Python-urllib 403 and production delivery are external limits, not scenarios.

`docs/website-workflow.md` step 5 is amended to say that `npm run check` is the narrow offline scenario check set and is distinct from the prohibited static-site regression suite. `docs/current-state.md` records the scope of `npm run check` and a baseline record: the commit the baseline ran on (a full 40-character commit hash present in this repository, the handoff commit under test), the Node and Python versions used, and every pre-existing failure with its diagnostic, or the word "none" when there are none.
