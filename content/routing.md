# Context routing endpoint

`POST /route` accepts `Content-Type: application/json`. Use [context.schema.json](/context.schema.json) for field types, [selection-index.json](/selection-index.json) for exact profile IDs and [recommendations.json](/recommendations.json) for task-based editorial defaults and conditional alternatives. Supply extracted requirements already known to the visiting agent. Omitted fields remain unknown; they are never assumed false in the response policy. Do not send conversation transcripts, source code, personal data or secrets.

Example:

```sh
curl --json '{"goal":"choose","component":"web","use_case":"live-web","realtime":true}' https://stack.menu/route
```

The response includes the selected journey (`choose`, `build`, `migrate`), direct resource links, curated candidates and explicit exclusions, contextual nudges, missing consequential questions and a handoff checklist. Catalogue candidates are not a flat ranking. For `goal:choose`, optional `use_case` with `ecosystem` or `mobile_platform` preferences returns an editorial primary, its reason and tradeoff, plus conditional alternatives from the recommendation policy. It does not analyze prose; infer the main job from supplied context. A primary may be excluded by a hard constraint; resolve the conflict rather than silently switching to an alternative. If no use case is supplied for a web choice, the endpoint asks whether the job is content publishing, an integrated product, live multiuser work, data/admin or a frontend for an existing API. Language and team preferences narrow the task. A live-session flag adds checks for reconnects, authorization, bounded fanout, persistence and overload. Phoenix is suggested for comparison only for an explicit web choice when Phoenix survives supplied UI and hosting constraints. This does not eliminate other frameworks or assert tested scale. When building with a chosen stack or migrating to an explicit target, task defaults do not replace that choice; checks stay within those choices.

`use_case` is an optional stable task ID from [recommendations.json](/recommendations.json). Its `component` must agree with an explicitly supplied component. `required_roles` lists the confirmed component roles the task needs. The neutral Mobile app task keeps a shared iOS/Android client and single-platform clients open while `mobile_platform` is omitted, asks which scope is intended and marks its editorial primary `conditional:true`. A supplied component can narrow candidate roles, but it does not answer the shared-versus-native question. Explicit `mobile_platform:shared` requires both roles; `ios` or `android` requires only that platform. A policy profile becomes a feasible candidate only when it documents the confirmed roles and satisfies the submitted hard constraints. A missing candidate/profile is a coverage gap, not permission to relax requirements. Policy alternatives are explanations of when another profile or composition may fit; they do not claim application compatibility. The optional field affects recommendations only when the resolved journey is `choose`; an existing-stack build or explicit migration keeps its authority.

Use `goal:auto` (or omit it) to build with an `existing_stack`, migrate when a `target_stack` is supplied, or choose otherwise. Explicit `choose` with `existing_stack` means the user has asked to reconsider it. `build` preserves a chosen stack; constraints prompt fit verification. `migrate` fetches source/target contracts and asks for missing inventory. It assesses documented component roles and profile responsibilities, rather than language overlap: a web-to-CLI or native-to-API pairing needs a declared replacement boundary and a retained interface/composition, or an explicitly changed product surface. A web component means the web application, including its documented server runtime; moving a server/full UI profile to a client-only browser profile therefore needs an explicitly retained backend/interface or an intended product-surface change. An explicit API component may narrow a composed source profile to its server responsibility when the source documents an API role. A UI architecture field describes the requested target architecture; it does not by itself narrow the source replacement boundary. Otherwise all documented responsibilities remain in scope. Target component, web UI, static-hosting and browser offline constraints produce conflicts and clarification questions while preserving the selected target and both profile resources. They never authorize an automatic alternate target. Responsibility overlap is documentation guidance, not application compatibility evidence. A backend is selected separately from native/offline/static clients. For mobile stack selection, send `use_case:cross-platform-mobile` and `mobile_platform:shared` when one client targets both iOS and Android. Use `ios` or `android` preferences only for an intended platform-specific client. Scope client and backend components separately for build/migration work; an iOS/Android component label alone does not select a native-only architecture. Explicit reconsideration with an existing stack links the baseline and migration contracts. Building preserves it even for live-session requirements; a mismatched component is a separate design question. A migration without a target asks for one; identical profile IDs prompt an installed-version/contract check instead of pretending a replacement is planned.

A UI architecture preference applies only with explicit `component:web`; API and unspecified components are not excluded by that preference.

`GET /route` describes the contract. A GET query supports the same fields (`?component=web&realtime=true`) for read-only tools; booleans must be literal `true` or `false`. Prefer POST for context because URLs can enter provider request logs. No user-agent detection, cookies, account, model call or application persistence is used.

HTTP: 200 result/contract; 400 invalid JSON, unsupported values/fields or duplicate query fields; 413 body exceeds 16 KiB; 415 wrong media type; 405 unsupported method. Responses are JSON and no-store. HEAD returns headers without a body. On failure, read this schema, correct the field and retry; if POST is unavailable, follow [the static agent entry](/agents/guide.md) and selection workflow directly.

This local implementation shares the same handler with the prepared Cloudflare Pages Function. A static download includes the full guides and policy; `/route` requires the local server or future Pages Function deployment.

The endpoint serves agent HTTP clients and same-origin use. Cross-origin browser POST/OPTIONS is not supported; those clients can use the static guides. Repeated GET fields are rejected; duplicate keys in a JSON object follow the JSON parser’s last-value behavior, so send each field once.


## Task preferences and rewrite sources — schema 1.1

The catalogue has nine task choices. Optional `ecosystem` values are `any`, `python`, `php`, `ruby`, `elixir`, `react` and `rust`; each task publishes the values it supports in `constraints`. `mobile_platform` is `shared`, `ios` or `android`. Read the task's `overrides` instead of assuming a language preference always changes the primary. Optional `alternative_ids` on a task or override select its applicable alternatives; the browser and endpoint use the same resolved list. Unreviewed preferences remain a question, not a verified fit. These fields affect choosing only; a build or explicit migration target remains authoritative.

Older `python-api`, `react-fullstack`, `ios` and `android` use cases map through `recommendations.json.aliases` to a neutral task with the original preference. Conflicting explicit preferences must be resolved; they do not silently replace the old meaning. Human links use the canonical task and preference after resolving an alias.

`existing_stack` accepts a guide ID, a source ID from [rewrite/sources.json](/rewrite/sources.json), or a bounded unlisted-system identifier. Optional `source_label` is a short display label, not an application transcript. An unknown source returns an inventory/research question; it never gets matched by language. `existing_source` returns the known source reference or explicit coverage gap. `target_stack` still accepts only the 16 full-guide profile IDs; source-only coverage does not imply target eligibility.

The initial added sources are Create React App, AngularJS, Vue 2, WordPress and WooCommerce. Each source has HTML, complete Markdown and JSON linked by its record. WordPress and WooCommerce are not classified as obsolete. Scope their installed versions, plugins, publishing and commerce behavior. A source's documented responsibilities always prompt an actual inventory: what is kept, replaced or retired, who owns it, how interfaces connect and which checks/rollback apply. A completed form is not compatibility evidence. Same-profile work can be an upgrade, not an invented cross-stack replacement.

Before building or rewriting, briefly consider whether an existing service or specialized tool already meets the need. This reminder does not create a required decision stage or override the user's instruction to build or rewrite.

An explicit API, CLI, automation, iOS or Android component can identify its task when `use_case` is omitted. Ambiguous web requirements still need a task; supplied preferences remain visible as unresolved context instead of being discarded.
